## 为什么做这个

做开发和 QA 时，经常要检查验证码、登录链接、通知邮件。单次测试，打开一个临时邮箱网页就够了；接进自动化以后，麻烦才开始出现：每家接口不同，地址与会话要保存，邮件列表和正文可能分开返回，脚本还得自己处理轮询、超时和重复创建。

我希望把这条流程收进同一个地方：**创建邮箱 → 持续取件 → 等待目标来信 → 读取正文和提取结果**。平时可以开网页看邮件，自动化则调用同一套 API，两边共享邮箱状态。

## 现在能做什么

- **集中管理邮箱和邮件。** 三栏分别放邮箱、邮件列表和正文，可以查看有效期、同步状态与来源错误。
- **用一套 API 调用不同来源。** 创建地址、列信、读取正文、等待邮件和实时事件都有统一入口；部分来源支持自定义前缀，留空随机生成。
- **把“等邮件”交给服务端。** 按发件域名、主题或正文设置条件，任务持久化保存；关闭网页不会取消等待，命中后返回明确的邮件 ID。
- **查看验证码与链接候选。** 提取结果保留来源位置和规则信息，有歧义时展示候选，方便核对原文。
- **给自动化单独授权。** 可以签发限制到某个邮箱的访问令牌，来源密钥留在服务端。
- **本机 SMTP 测试。** 自带本地收件能力，可以测试自己应用的发信流程，不必每次依赖外部邮箱服务。
- **中英文、浅色和深色主题。** 语言与主题选择会保存，也做了移动端布局。用户标签和邮件正文保持原文。

界面坚持黑白配色，主要想让地址、状态和正文容易扫读，长时间开着也清楚。

## 关于“97 个适配器”，先说清楚

当前目录收录 **127 个外部来源，已实现 97 个适配器**。其中 61 个无需平台密钥，34 个需要自己的平台凭证，2 个需要自部署配置。

这里的 97 指协议适配实现数。上游是否在线、域名是否被目标网站接受、邮件是否实际投递，是另外几件事；同一个来源今天可用，也可能明天改接口。因此，工作台会区分接入条件、实现情况与最近实测，具体兼容性仍需要按自己的场景验证。

截图使用合成演示数据，展示的是界面与流程，不是第三方投递成功的证据。

## 技术实现

前端是 **React + TypeScript + Vite**，后端是 **FastAPI + PostgreSQL**，取件由独立 worker 执行。邮箱、邮件、异步操作和等待任务都保存在服务端；通过任务租约、收件序号和明确的终态处理重复执行、旧邮件匹配及超时问题。

API 创建邮箱返回异步操作资源，等操作完成后再使用邮箱。后续可以创建等待任务，命中时读取对应邮件正文。README 和 API 指南里有完整调用示例。

## 怎么运行，Linux 支持到哪一步

仓库默认介绍已经改成中文，也保留了英文文档、架构说明和 API 指南。

当前一键启动脚本面向 **Windows**。**Linux/macOS 提供手动部署说明**，需要自行准备 PostgreSQL、构建前端并启动 API 与 worker。GitHub Actions 在 Ubuntu 上执行构建、测试和源码包检查；完整的 Linux 安装与桌面使用流程还需要更多实机反馈。目前已有 402 项自动化测试，本次开源整理后的 CI 已跑通。

手动部署说明：https://github.com/wuchenwl/linsemail/blob/main/docs/architecture.zh-CN.md#手动部署

默认服务面向本机工作站，适合开发、QA 和邮件流程验证。若要部署成公网多人服务，还需要补齐相应的隔离、鉴权和运维设计。
